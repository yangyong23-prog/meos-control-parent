# 缓存模型最终集成设计

## 2026-07-18 新迁移方向

末端、照明从“旧表与新版表双写、未 READY 读取旧缓存”调整为“只构建新版表、未 READY 实时查询”。READY 仍是是否消费新版缓存的唯一状态；未 READY 分支不再访问旧版运行结果缓存。其他运行监测系统继续保持旧链路。

该调整影响直接策略、模板对象重建、规则扩展和所有 READY 路由。`cache_info_code_template` 继续保存模板过滤元数据。末端白名单改为只使用新版白名单 Key 保存配置对象范围；未 READY 时先读取配置 ID，再实时查询 RWD，READY 后直接读取新版对象。

## 集成边界

云端负责七张新版缓存表的写入、单类型完整构建、构建成功后的数据库/Redis `READY` 状态和末端/照明四类读取路由。云端和边缘端各自携带同版本、同内容的七表 Flyway；边缘端只消费云边同步后的数据和 `READY`，不实现七表同步或边缘完整性核验。末端白名单空间只使用独立 `WHITELIST_*` 新版缓存键保存配置范围和参与 READY 读取路由。

## 验收路径

1. 写入链路：RWD/模板/规则远程计算由调用方在事务外完成；对象模型写服务把对象 Key 替换和通用关系替换拆成独立入口。对象入口接收完整 RWD 对象快照和可选扩展动作，使用统一转换器在事务前生成对象与模型视图记录，再在同一短事务内提交对象、视图、Key 关联和扩展动作；关系入口接收一个关系枚举和一组以 `id/relObjIds` 表示主体及完整目标的 RWD 对象，并在独立短事务中替换该关系范围。写服务不得持有 RWD 客户端或自动发起关系查询，调用方也不得构造对象、模型视图或关系资源层参数。末端、照明不再写入 `cache_rwd_object`、`cache_iot_rule` 等旧版运行结果缓存。
2. 启用链路：仅 `AIR_TERMINAL`、`LIGHTING` 的单类型全部策略返回成功后，在同一个构建锁内持久化 `READY` 并刷新云端 Redis，完成后才释放锁；调度层必须合并每个策略的 `boolean` 结果，任一策略返回 `false` 或抛出异常都按构建失败处理，保持原数据库和 Redis 状态且不写 `FAILED`。云端 Debug 只保留当前请求集团和项目上下文中的单类型 init，不进入 XXL-JOB 遍历；边缘继续只收敛缺失状态。云端 READY 启动恢复与边缘启动/30 秒收敛任务类共用 `@ConditionalOnProperty(prefix = "project.cache.rwd", name = "enabled", havingValue = "true", matchIfMissing = true)`；关闭时两个自动任务 Bean 都不注册，不影响手动构建和 READY 提交。条件只在应用上下文启动时判定，开关变更后两端都必须重启。
3. 读取链路：末端和照明在 `allowCache()`、Redis `READY` 且类型受支持时读新表；未 READY 时调用现有对象或规则实时查询，不访问旧版持久化运行结果缓存，实时服务内部既有 Redis 短缓存可以继续生效。规则业务读取按对象 ID、目标信息点和云边规则类型直接查询 `cache_rule`，不通过 Key 关系表限定场景。末端空间范围只由 `SPACE_RANGE_TERMINAL` 壳配置选择白名单 Key/项目全量 Key，`AirTerminalSpaceWithStatusQueryParam` 和 `RunningMonitorSpaceQueryParam` 都不接收范围开关；调用方按配置选择固定白名单或项目全量策略入口，不能根据 Key 是否命中反推。白名单 Key 为空时返回空空间。缓存构建的 `useCache=false` 始终计算项目全量空间。独立模型视图字段接口在 READY 时只读取 `id`、`view_data` 并平铺实际存储字段，未 READY 时按对象 ID 实时查询 RWD。末端白名单配置使用的全量候选接口不受当前白名单模式影响，READY 时读取项目全量空间 Key，未 READY 时实时计算，并只投影四个基础字段。READY 请求不回退旧表或 RWD，其他系统保持旧链路。
4. 重建链路：末端白名单配置先按本次入参 ID 在内存完成实时数据补全和校验，再只替换新版白名单 Key；准备失败不得覆盖上一版新版白名单。首版升级若数据库尚无 `AIR_TERMINAL READY` 且新版 Key 为空，先读取旧对象表；旧白名单 Key 有有效配置 ID 即按历史模式直接实时补全，并在新版 Key 替换事务内补写 `WHITE_LIST`，不能先读取缺失壳配置的默认 `FULL`。无旧 ID 时再按当前壳配置处理；数据库 READY 后旧表永久失去配置权威性。全量重建由内部 `useCache=false` 分支明确调用项目全量 `listSpaces(...)`，同时设置 `meosCache=false` 防止反读上一版新缓存；两个开关都不作为白名单范围参数。
5. Key 级替换：每个新版缓存 Key 先由调用方在事务外计算完整对象快照和关系对象，再分别调用对象入口与关系入口；对象快照为空时只删除该新版 Key 的关联，关系对象集合为空表示本次不维护该关系类型，单个关系对象的 `relObjIds` 为空仍表示明确清理该主体和关系类型。对象、模型视图和已经不可达的无 Key 关系记录不做全局孤儿清理。照明关系不枚举其他 Key：服务空间和楼层按回路主体 ID 删除，控制模块和 DDC 按回路目标 ID 删除，再插入当前 Key 的完整查询结果；多个 Key 命中同一关系时允许各自重复执行。
6. 异常边界：显式末端、照明手动初始化保留并上抛策略、SQL 和事务原始异常；同步 DTX 事件监听器记录异常和 `false` 结果，不把缓存故障抛回发布请求。
7. 性能边界：缓存 Mapper 多值写入统一按 1000 条分片；最多几千个主键、对象 ID 或缓存 Key 的普通 `IN` 读取一次完成，模板明细、规则完整业务键及关系范围等复合 `OR` 条件继续按 500 条控制 SQL 长度。查询仍命中迁移定义的项目、缓存键、对象、关系主体/目标、模板业务键和规则索引。
8. 结构边界：云端和边缘端使用同名、同版本、同内容的 Flyway 创建七张表；同步项目组只负责数据同步接入，不代替本项目维护边缘数据库结构。

## 已知限制

独立七表数量核验已经取消；`READY` 表示该支持类型的完整构建流程在构建锁内成功结束并完成状态持久化与 Redis 刷新，不额外证明七张表字段或 JSON 内容与外部源逐项一致。真实 RWD、Redis 和 Spring 业务集成仍需通过聚焦回归命令验证。

对象、模型视图和通用关系可能保留已经没有 Key 引用的历史记录；当前读取先由新键关联限定直接对象范围，因此这些不可达记录不会扩大业务返回。照明关系只由触发重建的 Key 按自身回路范围删除并重建，不额外协调其他 Key。本轮不增加全局清理器，后续如需控制存储空间应单独设计可验证的离线维护任务。
