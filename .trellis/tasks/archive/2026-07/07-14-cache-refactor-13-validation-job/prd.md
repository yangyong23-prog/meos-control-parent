# 缓存数量核验与云端启用（已取消）

## Goal

保留原“七表数量核验与云端启用”任务目录用于历史追溯。该方案已取消，不再交付数量核验、差异报告、`FAILED` 生产写入、手动校验 XXL-JOB 或 Debug validate。

## Superseded Decision

- 原方案计划按“集团 + 项目 + 一级类型”重新计算七张新表期望数量，并与数据库实际数量比较后决定是否启用。
- 最新契约改为：仅 `AIR_TERMINAL`、`LIGHTING` 的单类型完整构建成功后，在同一个构建锁内直接持久化 `READY` 并刷新云端 Redis，完成后才释放锁。
- 缓存策略、RWD、SQL、事务、状态持久化或 Redis 刷新失败继续按现有异常边界传播；数据构建失败不得修改原数据库或 Redis 状态，也不得写入 `FAILED`。
- `FAILED` 只允许作为历史数据或测试手工 Redis 非 READY 值兼容读取，不再由生产流程写入。
- 云端 Debug 缓存控制器只保留当前集团、当前项目、必填单类型的 init 入口，不提供 validate 入口。
- READY 恢复、边缘缺失 Key 收敛以及末端/照明读取路由继续保留，由对应子任务维护。

## Historical Scope

以下内容仅用于解释旧任务为何存在，不再构成实现或验收要求：

- 七张表 `expectedCount`、`actualCount` 和差值比较；
- 逐表数量日志或核验报告；
- 首次失败持久化 `FAILED`；
- 独立手动校验处理器、参数入口和 Debug validate；
- 通过数量一致性决定 `READY`。

## Acceptance Criteria

- [x] 已在本目录记录原数量核验方案被“构建成功直接 READY”替代。
- [x] 生产代码中不再注册或调用数量核验任务，不再写入 `FAILED`，也不暴露 Debug validate。
- [x] 支持类型完整构建成功后在构建锁内提交 `READY` 并刷新 Redis；构建失败保持原状态。
- [x] 父任务、集成任务、状态基础、初始化、边缘收敛和后端规范均使用同一最新契约。

本历史任务不再阻塞子任务 14 或最终集成。目录保留用于追溯需求变更，实际实现与验收统一归入初始化及集成任务。
