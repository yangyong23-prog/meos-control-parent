# 安防运行监测性能优化设计

## 设计概览

本任务复用现有缓存对象模型和需求配置结果，不新增另一套安防专用表。整体读取链路分成三层：

1. 稳定数据：设备、空间、建筑楼层字段、设备-空间关系和前端当前使用的模型图字段由统一静态读取链路提供。
2. 可预计算配置：`ARMING`、`PASSING` 的继承结果由 `demand_config_result` 提供。
3. 动态数据：IoT 值、孪生规则和异常事件在请求期实时查询，与前两层按对象 ID 合并。

```text
RWD/DTX 发布
    -> 安防缓存构建与范围替换
       -> cache_object + cache_object_key_rel
       -> cache_object_rel
       -> cache_object_model_view
       -> SECURITY READY

需求配置/模板/空间层级变更
    -> 安防需求结果刷新
       -> demand_config_result/snapshot

接口请求
    -> SECURITY 静态缓存就绪判断
       -> 未就绪：完整旧 RWD 静态路径
       -> 已就绪：静态缓存路径
    -> 固定读取需求配置结果
    -> 实时读取 IoT/规则/异常事件
    -> ID 关联与一次聚合
    -> 保持原响应契约
```

## 数据契约

| 数据 | 存储/来源 | 关键字段 | 更新方式 |
|---|---|---|---|
| 安防设备 | `cache_object`，Key=`SECURITY_LIST_EQUIPMENT` | `id`、`local_name`、`class_code`、`monitoring_surveillance_status`；JSON 扩展静态信息点 | 全量初始化 + DTX/RWD 增量范围替换 |
| 安防空间 | `cache_object`，Key=`SECURITY_LIST_SPACE` | `id`、`local_name`、`building_id`、`floor_id`、`monitoring_surveillance_status` | 全量初始化 + DTX/RWD 增量范围替换 |
| 设备服务空间 | `cache_object_rel` | 主体设备、`service_space`、目标空间 | 按设备关系范围替换 |
| 设备所在空间 | `cache_object_rel` | 主体设备、`in_space`、目标空间 | 按设备关系范围替换 |
| 模型图字段 | 与设备静态响应一起组装；底层可复用现有模型视图存储 | `bimId`、`bimLocation`、`outline` | 随设备对象初始化/变更同步 |
| 需求最终配置 | `demand_config_result` / snapshot | 模板、实例类型、实例 ID、最终配置、屏蔽/黑名单等 | 复用配置结果刷新机制并扩展安防类型 |
| IoT/规则/异常事件 | 现有实时服务 | 请求涉及的对象 ID 与 infoCode | 请求期查询，不写入上述静态表 |

所有表查询必须带项目范围。静态响应可在服务端把已有模型视图数据与设备对象按 ID 批量组装，但对外只暴露一个设备响应；本期不增加模型图专用 HTTP 请求，也不要求前端二次合并。动态运行态字段仍不得进入静态对象缓存。关系编码通过项目常量/枚举表达，业务代码不散落字符串字面量。

## 构建与就绪

新增或扩展安防缓存策略，按一次重建事务的逻辑顺序完成：

1. 拉取 12 类安防设备，只投影接口消费字段。
2. 拉取空间，并保留建筑、楼层和本地名称。
3. 根据设备类型批量拉取 `service_space` 与 `in_space` 关系；每个关系方向一次提交完整对象范围，由 RWD 客户端统一分页。
4. 转换全部对象和关系成功后执行项目范围替换；转换失败不得先删除旧范围。
5. 完整写入后标记 SECURITY READY。任一步失败保留未就绪或原可用版本，并记录可重试错误。

增量事件要么按受影响对象和关系范围幂等替换，要么触发项目级重建。删除事件必须同时清理 Key 关联、对象关系和关联模型图数据。具体选择以现有缓存构建框架支持的最小一致范围为准。

## 读取路由

| 消费方 | READY 读取 | 继续实时读取 |
|---|---|---|
| `/security/function` | 设备类型及 `hasArmingFunc`、`cameraType` | 无 |
| `/security/listDeploymentSpace` | 设备、`service_space`、`in_space`、空间 | 无 |
| `/security/listAccessSpace` | 门禁、`in_space`、空间 | `accessDemand`、`equipOnSet` 规则存在性 |
| `/security/listEquipment` | 12 类设备及前端当前使用的模型图字段 | 无新增请求；在同一响应内完成组装 |
| `/security/dashboard` | 受控空间、关联设备、建筑/楼层字段 | 空间撤布防状态 |
| 设备统计 | 6 类设备 | 4 个状态信息点和异常事件 |
| 安防需求查询 | 预计算最终配置 | 无；结果 miss 按无配置处理 |

SECURITY READY 判断只控制静态对象读取，并在业务入口完成。同一请求选定静态新旧路径后不得因某个缓存列表为空而自动穿透；空列表是合法业务结果，数据库异常则正常向上抛出。只有明确的静态缓存未就绪状态使用旧 RWD 路径。

## 需求配置结果

将 `ARMING`、`PASSING` 加入现有结果刷新仓储的统一支持集合，所有 Listener、初始化 Job、Debug 入口和仓储保护复用该集合，不能分别硬编码支持类型。

结果计算继续以既有实时 Gateway 为权威生成来源，保持模板日期、四级继承、屏蔽和黑名单语义。读取逻辑固定按模板与空间 ID 批量查询结果，结果 miss 按真实无配置处理，不增加独立 READY 状态，不回退 `listConfigsByInstances`，也不根据结果表是否为空推断就绪。配置、模板、黑名单、屏蔽对象或空间层级变化复用结果刷新机制局部或全量重算。

## 内存聚合与动态查询

### 通行空间

将门禁规则结果转换为两个设备 ID 集合，再通过 `in_space` 关系构造空间聚合状态：

```text
hasAccessDemandEquipmentIds
hasEquipOnSetEquipmentIds
equipmentId -> spaceIds
spaceId -> { hasAccessDemand, hasEquipOnSet }
```

每条设备关系最多处理一次，最终保留两个标志均为真的空间。该算法允许两个标志来自不同设备，避免对每个空间反复扫描全部关联门禁。循环内不输出 INFO 日志，只在阶段结束记录数量和耗时。

### 设备统计

先从设备缓存完成类编码、监控状态、实时流协议等静态过滤，生成去重后的目标设备 ID 集合，再查询四个动态信息点。优化顺序为：

1. 验证底层查询是否因无关对象、查询条件或索引造成全量扫描。
2. 优先在共享查询实现中消除重复扫描或增加合适的批量读取路径。
3. 只有基准测试证明有收益时才按对象 ID 有界拆批并行，避免并发放大下游压力。
4. IoT 与异常事件各自在异步任务内生成局部 Map，`allOf().join()` 后由当前线程合并，避免并发写普通 Map。

不能用长生命周期业务缓存替代动态查询。允许复用 IoT 服务自身对实时数据的既有缓存语义。

## 模型图字段兼容

设备接口保持前端现有模型图消费契约，普通设备字段和 `bimId`、`bimLocation`、`outline` 在一次响应中返回。若底层继续使用 `cache_object_model_view`，服务端必须按设备 ID 批量读取并在内存中组装，禁止逐设备查询；若已有对象快照已包含这些字段，则直接沿用。前端无需新增调用或改变过滤时机。

## 兼容与回滚

- 对外 Controller 路径、请求参数和响应 DTO 默认不变；设备接口继续一次返回模型图字段。
- 静态缓存读取由 SECURITY READY 控制；需求结果读取不设 READY，回滚时恢复调用方读取入口，不以结果表是否为空切换路径。
- 缓存构建失败不得覆盖上一份完整数据；读取基础设施异常不得返回空集合掩盖故障。
- 对象集合去重时保留现有顺序契约；若接口没有顺序契约，测试按集合比较并保持输出稳定。

## 主要改动边界

- 安防服务与策略：`SecurityServiceImpl`、`RunningMonitorSecurityStrategy`、`SecurityDashboardQueryContext` 及对应接口/DTO。
- 统一缓存：安防缓存策略、对象/关系写入服务、状态服务和相关枚举/常量。
- 需求配置结果：支持类型、刷新入口、初始化与安防调用方。
- IoT 查询：仅在定位到共享瓶颈时修改 `AbstractIotDataCacheServer` 的实现或增加兼容批量能力。
- 前端适配不在当前仓库，作为现有设备接口字段完整性的联调依赖。

## 风险控制

- 静态缓存陈旧：用事件刷新、重建入口、就绪状态和对象数量日志保障可诊断性。
- 关系方向错误：针对 `service_space`、`in_space` 分别建立正反向查询测试，使用设备与空间固定夹具验证。
- 需求结果刷新完整性：复用统一初始化和监听器；结果 miss 按无配置处理，不以表非空推断就绪或回退实时继承。
- 动态查询并发放大：限制并发度并记录下游耗时、批次数和对象数。
- 云边不一致：若新增配置、状态或迁移，云端与边缘端保持同版本、同契约，并验证同步发布顺序。
- 模型图字段随设备数据返回会增加响应体积和序列化成本；性能报告需单独记录该开销，但不以拆分接口解决本期问题。
