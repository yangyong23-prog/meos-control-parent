## 三、各差异点详细分析

### 差异点 A：计算触发条件

#### 产品文档 v2.0 要求

同时满足三个条件才触发计算：

```
条件1：classCode 在计算范围内（通过配置过滤）
条件2：enableCtrl=1（联动启用）OR equipSwitchSet=1（单点开启）
条件3：消息的 status=0（开始执行）AND result=0（进行中）
```

**重要说明**：产品文档中的 `status` 和 `result` 是 MQTT 孪生消息携带的字段，代码中分别映射为：

- `status` → `dataStatus`（`@JsonAlias({"dataStatus", "status"})`）
- `result` → `result`

#### 现有代码实现（`ComputeIotDataHandler.checkComputeInfoCodeDataCondition()`）

```java
// CTRL 类型（控制消息）：有配置直接计算，无 status/result 检查
if (EnumIotDataType.CTRL.getCode().equals(source.getType()) && triggerFormulaInfo != null) {
    return true;
}
// FEEDBACK 类型（反馈消息）：仅 dataStatus=1（完成）触发
if (EnumIotDataType.FEEDBACK.getCode().equals(source.getType())) {
    if (source.getDataStatus() != 1) {
        return false;
    }
}
```

#### 条件对比

| 条件                             | 产品文档           | 现有代码                             | 差异类型     |
|--------------------------------|----------------|----------------------------------|----------|
| classCode 范围过滤                 | ✅ 明确前置条件       | ✅ 通过有无 triggerFormulaInfo 配置间接实现 | **逻辑等价** |
| enableCtrl/equipSwitchSet 前置过滤 | ✅ 前置条件（满足任一即可） | ⚠️ 不作前置过滤，在公式内部处理                | **时机不同** |
| status=0 AND result=0          | ✅ 核心前置条件       | ❌ 无此判断（用消息类型+dataStatus替代）       | **缺失**   |

#### 深入分析：`checkProcessData()` 与产品文档条件3的关系

代码中最接近产品文档条件3的判断在 `checkProcessData()` 方法中：

```java
// FeedbackInfoMsgMqttVO.java
public boolean checkProcessData() {
    return type == 1 && result == 0 && (dataStatus == 1) && ("8".equals(cmdLevel) || "12".equals(cmdLevel));
}
```

| 字段               | 产品文档 | 代码实际                                                                 | 对应关系      |
|------------------|------|----------------------------------------------------------------------|-----------|
| `status=0`（开始执行） | 核心条件 | **无此检查**（checkComputeInfoCodeDataCondition 不检查）                      | ❌ 缺失      |
| `result=0`（进行中）  | 核心条件 | `checkProcessData()` 中有 `result==0`，但仅用于 `checkControlRealStatus` 内部 | ⚠️ 不在前置过滤 |

#### 触发场景对比

| 场景                                     | 产品文档          | 现有代码             | 结果                      |
|----------------------------------------|---------------|------------------|-------------------------|
| 开启指令（CTRL，dataStatus=2 进行中）            | ✅ 触发（条件3满足）   | ✅ 触发（CTRL类型）     | **行为一致**                |
| 开启指令（CTRL，dataStatus=1 完成）             | ❌ 不触发（条件3不满足） | ✅ 触发（CTRL类型）     | **不同**                  |
| 设备反馈运行状态（FEEDBACK，dataStatus=1）        | ❌ 不触发（条件3不满足） | ✅ 触发（FEEDBACK完成） | **不同**                  |
| 设备开关未开启（enableCtrl=0，equipSwitchSet=0） | ❌ 不触发（条件2不满足） | ✅ 触发，公式返回0或3     | **不同**：代码会更新rcRunStatus |

**关键影响**：现有代码在 FEEDBACK 消息触发重新计算，实际上**覆盖了**产品文档"方式一：监听MQTT消息更新状态"的需求（见差异点D）。

### 差异点 B：runStatus=nil 时的状态返回值

#### 产品文档 v2.0 要求

联动控制和单点控制两个分支中均明确：

```
开关=1，onlineStatus=1，runStatus 值为空 → rcRunStatus = -1（无效）
```

#### 现有代码两条路径的实际行为

**路径1：sourceIotType=0（`checkControlRealStatus()`）**

| dataStatus | runStatus | 返回值                    | 与产品文档对比                   |
|------------|-----------|------------------------|---------------------------|
| 2（进行中）     | null（不读取） | `"2"`（开启中）             | 🔴 不同（直接返回2，不依赖runStatus） |
| 1（完成）      | null      | `null`（不更新rcRunStatus） | 🔴 不同（null不更新 vs -1主动推送）  |
| 1（完成）      | `"0"`     | `"0"`                  | ⚠️ 注意：产品文档期望2（开启中），代码返回0  |
| 1（完成）      | `"1"`     | `"1"`                  | ✅ 一致                      |

**路径2：sourceIotType=1（Aviator 公式）**

```javascript
// triggerFormula 中 equipSwitchSet=1 时
(runStatus == nil || runStatus == 0 ? 2 : 1)
// runStatus=nil → 返回 2（开启中）
```

| runStatus | 公式结果     | 与产品文档对比         |
|-----------|----------|-----------------|
| nil       | `2`（开启中） | 🔴 不同（产品文档期望-1） |
| 0         | `2`（开启中） | ✅ 一致            |
| 1         | `1`（运行）  | ✅ 一致            |

#### 设计文档与代码的一致性

`archive/design.md` 状态映射决策树：

```
值为 1 (设定为开启)
  └─ runStatus == nil ────▶ 返回 2 (开启中)
```

`spec.md` 需求1：

```
如果设定值为 1（开启）：实际状态为 0 或 nil → 返回 2（开启中）
```

**结论**：设计文档与代码一致，均与产品文档存在差异。这是**设计文档和产品文档之间最核心的分歧**。

#### 业务影响分析

| 场景                 | 产品文档（-1）  | 现有代码（2）    | 用户体验差异   |
|--------------------|-----------|------------|----------|
| 设备启动时尚未上报runStatus | 显示"无效/灰色" | 显示"开启中/黄色" | 代码体验更积极  |
| 设备故障，无法上报runStatus | 持续显示"无效"  | 持续显示"开启中"  | 代码可能误导用户 |

{判断设备是单点控制还是联动控制}

### 差异点 D：状态更新机制

#### 产品文档 v2.0 要求

当 rcRunStatus=2（开启中）时，**并行启动两种机制**：

```
方式一：监听 MQTT 消息（runStatus 变化）
  ├─ runStatus=1 → 更新 rcRunStatus=1，SSE推送
  └─ runStatus=0 → rcRunStatus=0，SSE推送

方式二：定时查询 runStatus（补偿机制）
  └─ runStatus=1 → 更新 rcRunStatus=1，结束定时查询，SSE推送
     （其他情况继续定时查询，产品图未明确超时策略）
```

#### 现有代码实现

| 机制             | 现有代码                   | 说明             |
|----------------|------------------------|----------------|
| MQTT 触发更新      | ✅ 通过 FEEDBACK 消息触发重新计算 | 功能等价于产品文档方式一   |
| 定时查询 runStatus | ❌ **完全不存在**            | 全项目无此机制        |
| 超时兜底           | ❌ **不存在**              | 设备可能永久停留在"开启中" |

#### 差异影响：MQTT 消息丢失场景

```
场景：设备启动成功，上报 runStatus=1，但 MQTT 消息丢失

产品文档（双重保障）：
  定时查询发现 runStatus=1 → 更新为1 → 状态最终一致

现有代码：
  只有 MQTT 路径 → 消息丢失 → 设备永久显示"开启中"（已知缺陷）
```

### 差异点 E：前端推送方式

#### 产品文档 v2.0 要求

产品流程图两处明确标注：`SSE推送rcRunStatus给前端`

#### 现有代码实现

**`WsMessageServiceImpl.pushMessage()` 实际路径**：

```java
// rcRunStatus 消息 webType = PARAM_SET（未被设置，使用默认值）
// → 走 WebSocket 推送路径
// → 不满足 PAGE_BROADCAST 或 INFO_EXTEND_SET 条件
// → 不走 SSE 推送路径
```

**结论**：rcRunStatus 消息**实际走 WebSocket，不走 SSE**。

#### 技术对比

| 推送方式      | 产品文档   | 现有代码           | 说明        |
|-----------|--------|----------------|-----------|
| SSE       | ✅ 明确要求 | ⚠️ 不满足条件，实际不触发 | 需确认产品意图   |
| WebSocket | 未提及    | ✅ 默认推送         | 功能上满足实时推送 |

> **待确认**：产品文档中"SSE推送"是技术规范要求，还是泛指"服务端实时推送"？
