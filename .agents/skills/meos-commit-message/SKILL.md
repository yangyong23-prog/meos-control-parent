# MEOS 提交信息规范

在 `meos-control-parent` 项目中创建或修改 Git 提交信息时，必须使用本 skill。提交信息由四个部分组成：迭代号、任务编号、操作类型、修改内容。

## 标准格式

有任务编号：

```text
[迭代号](任务编号)操作类型: 修改内容
```

示例：

```text
[7.260601.0](UYAI-928)fix: 运行概述环境品质无数据返回对象
```

用户明确确认不带任务编号时，省略任务编号括号：

```text
[迭代号]操作类型: 修改内容
```

## 生成步骤

1. 读取当前分支：

   ```bash
   git branch --show-current
   ```

2. 从当前分支解析迭代号。

   - 优先匹配 `v7.260601.0` 这样的片段，并去掉前缀 `v`。
   - 示例：`feat_v7.260601.0_复盘报告` -> `7.260601.0`。
   - 如果当前分支无法解析迭代号，不要猜测；询问用户迭代号。

3. 确认任务编号。

   - 如果用户已经提供任务号或 bug 编号，例如 `UYAI-928`，直接使用。
   - 如果用户没有提供，必须询问：“任务编号是什么？或者是否确认不带任务号提交？”
   - 用户明确确认不带任务号后，才允许使用无任务号格式。

4. 确认操作类型。

   常用类型：

   - `fix`：缺陷修复
   - `feat`：功能新增或能力变更
   - `docs`：文档或规范变更
   - `refactor`：重构，行为不变
   - `test`：测试相关
   - `chore`：构建、依赖、工程杂项

   操作类型后使用英文冒号 `:`，冒号后保留一个空格。

5. 生成修改内容。

   - 使用简洁中文描述。
   - 优先根据用户描述、diff 内容和近期提交风格生成。
   - 不要把文件名、实现细节、长句塞进提交信息。

6. 无论操作类型是什么，必须向用户展示提交说明。

   提交说明必须包含：

   - 变更原因：说明本次提交产生的业务背景、技术背景、需求来源或触发条件。
   - 变更方案：说明本次通过什么方式完成变更，保持简洁，不堆砌实现细节。
   - 影响范围：说明受影响的功能、接口、页面、数据范围、配置、流程或用户场景。

   提交说明只用于让用户理解本次提交背景，不作为提交确认项；不需要用户单独确认，也不要因为提交说明不完整而追问用户。

   如果仅凭用户描述和 diff 无法确认某一项，不要编造；按当前可判断的信息如实描述，无法判断的字段写“当前信息未体现”。

7. 提交前必须让用户确认最终提交信息。

   提交前展示：

   ```text
   提交说明：
   - 变更原因：运行概述环境品质查询在无数据时未返回约定的空对象。
   - 变更方案：补齐无数据分支的返回对象构造，保持响应结构一致。
   - 影响范围：影响运行概述中环境品质无数据场景的前端展示和接口消费。

   将使用以下提交信息：
   [7.260601.0](UYAI-928)fix: 运行概述环境品质无数据返回对象

   请确认是否提交。
   ```

   所有操作类型都必须展示“提交说明”。提交确认只针对最终提交信息和是否执行提交；只有用户确认后，才执行 `git commit` 或 `git commit --amend`。

## 禁止事项

- 不要使用 `fix.`、`feat.` 这种点号格式。
- 不要在用户未提供任务号时自行编造任务号。
- 不要在未确认提交信息时直接提交。
- 不要从最近提交中复制任务编号，除非用户明确确认。
- 不要因为分支名里有中文描述就把它当作修改内容；修改内容应来自本次改动。
- 不要为了补齐提交说明而编造变更原因、变更方案或影响范围。
